# 故障应急响应预案

## 1. 概述
本预案定义抖音电商数据监控平台的故障分级、响应流程、职责分工、升级机制及演练要求，确保故障能在最短时间内被发现、定位、恢复。

---

## 2. 故障分级标准

### 2.1 严重度定义 (参考 Google SRE / PagerDuty)

| 级别 | 代码 | 定义 | 典型场景 | 响应时限 | 恢复目标 (RTO) |
|------|------|------|---------|---------|---------------|
| **P0 - 紧急** | SEV-0 | 核心业务完全中断、数据丢失、安全事件、全站不可用 | MySQL 主库宕机、数据泄露、勒索软件、核心 API 全部 5xx | **15 分钟** | < 30 分钟 |
| **P1 - 高危** | SEV-1 | 核心功能严重受损、大量用户受影响、关键指标异常 | 同步任务连续失败、API 错误率 > 10%、Redis 集群故障、证书过期导致 HTTPS 失效 | **1 小时** | < 2 小时 |
| **P2 - 中危** | SEV-2 | 部分功能异常、少量用户受影响、性能显著下降 | 单接口超时、告警风暴、单 Worker 离线、磁盘空间不足 | **4 小时** | < 8 小时 |
| **P3 - 低危** | SEV-3 | 非核心功能异常、体验受影响但有绕行方案、观测盲区 | 非关键报表失败、日志采集中断、文档链接失效、UI 样式错乱 | **1 个工作日** | < 3 个工作日 |

### 2.2 影响范围判定
| 影响范围 | 判定标准 | 示例 |
|---------|---------|------|
| 全站 | 所有用户、所有店铺、所有功能 | MySQL 主库宕机、SLB 故障 |
| 多租户 | > 50% 店铺、> 50% 用户 | Redis 集群故障、核心 API 降级 |
| 单租户/模块 | 单店铺、单功能模块 | 单店铺同步失败、合规检测异常 |
| 内部/运维 | 仅运维/开发人员感知 | 监控指标缺失、CI/CD 失败 |

## 4. 故障响应流程 (标准化)

### 4.1 发现与上报
```
发现渠道：
├── 监控告警 (Prometheus Alertmanager → WeCom/PagerDuty)
├── 用户反馈 (客服工单 / 企业微信群)
├── 主动巡检 (运维日常巡检 / 代码发布后验证)
└── 第三方通知 (上游 API 通知 / 安全厂商通报)

上报格式：
[故障等级] [影响范围] [简述] [发现时间] [发现渠道] [初步判断]
示例：[P1] [多租户] [订单同步任务连续 3 次失败] [2026-09-26 10:30] [Prometheus告警] [疑似 FXG API 限流]
```

### 4.2 响应生命周期
```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        故障响应生命周期                                        │
├─────────────┬─────────────┬─────────────┬─────────────┬─────────────────────┤
│   发现/上报  │   分析/定位  │   恢复/缓解  │   验证/收尾  │   复盘/改进        │
│   (T+0)     │   (T+15min) │   (T+RTO)   │   (恢复后)   │   (T+24h/48h)      │
├─────────────┼─────────────┼─────────────┼─────────────┼─────────────────────┤
│ • 告警触发  │ • IC 确认级别 │ • 实施恢复方案 │ • 业务验证   │ • 根因分析 (5Why) │
│ • 自动分派  │ • TL 技术分析 │ • 并行缓解措施 │ • 监控观测   │ • 产出 PIR 文档   │
│ • 群通知    │ • 影响评估    │ • 状态同步     │ • 通知恢复   │ • 改进项跟踪      │
│ • 记录时间戳│ • 升级决策    │ • 变更记录     │ • 关闭工单   │ • 知识库更新      │
└─────────────┴─────────────┴─────────────┴─────────────┴─────────────────────┘
```

### 4.3 关键时间节点 (SLA)
| 节点 | P0 | P1 | P2 | P3 |
|------|-----|-----|-----|-----|
| 首响应 (ACK) | 5 min | 15 min | 1 h | 4 h |
| 定位根因 | 15 min | 30 min | 2 h | 8 h |
| 实施恢复 | 30 min | 2 h | 8 h | 24 h |
| 业务验证通过 | 45 min | 3 h | 10 h | 48 h |
| 发布 PIR 初稿 | 4 h | 8 h | 24 h | 72 h |

## 5. 常见故障场景与标准处理流程

### 5.1 数据库故障
| 故障现象 | 诊断步骤 | 标准处置 | 升级条件 |
|---------|---------|---------|---------|
| MySQL 主库不可连接 | 1. 检查进程/端口<br>2. 检查磁盘/内存/CPU<br>3. 检查错误日志<br>4. 尝试重启 | 1. VIP 漂移到从库<br>2. 修改 DNS/配置指向新主<br>3. 通知业务只读降级<br>4. 修复旧主重建从 | 5min 内未恢复 → P0 升级 |
| 复制延迟 > 30s | 1. `SHOW SLAVE STATUS`<br>2. 检查长事务/大事务<br>3. 检查网络/IO | 1. 暂停写入流量<br>2. 杀掉阻塞事务<br>3. 调整并行复制参数<br>4. 必要时重做从库 | 延迟持续 > 5min → P1 |
| 磁盘空间 > 90% | 1. `df -h` 定位大文件<br>2. 清理 Binlog/慢查询日志<br>3. 归档历史分区 | 1. 扩容磁盘 (云盘在线扩容)<br>2. 清理临时表/归档数据<br>3. 调整保留策略 | 空间 > 95% 且无法清理 → P0 |

### 5.2 Redis 故障
| 故障现象 | 诊断步骤 | 标准处置 | 升级条件 |
|---------|---------|---------|---------|
| Redis 主节点宕机 | 1. Sentinel 日志确认<br>2. 自动故障转移观察<br>3. 客户端重连验证 | 1. 确认 Sentinel 自动切主<br>2. 检查客户端连接池刷新<br>3. 验证缓存命中率恢复 | 自动切换失败 → P0 手动干预 |
| 内存使用 > 90% | 1. `INFO memory`<br>2. `MEMORY DOCTOR`<br>3. 大 Key 分析 | 1. 淘汰策略生效确认<br>2. 手动删除大 Key/过期 Key<br>3. 扩容或分片 | OOM 重启 → P0 |
| 连接数耗尽 | 1. `CLIENT LIST` 统计<br>2. 识别泄漏客户端<br>3. 调整 `maxclients` | 1. 重启泄漏服务实例<br>2. 临时调大限制<br>3. 修复连接池配置 | 业务大面积报错 → P1 |

### 5.3 应用服务故障
| 故障现象 | 诊断步骤 | 标准处置 | 升级条件 |
|---------|---------|---------|---------|
| API 错误率飙升 | 1. Grafana 看错误率/延迟<br>2. 日志检索错误堆栈<br>3. 关联最近变更 | 1. 回滚最近发布<br>2. 熔断下游依赖<br>3. 限流保护核心接口 | 回滚无效 → P0 架构师介入 |
| Celery 任务积压 | 1. Flower 查队列长度<br>2. Worker 存活检查<br>3. 任务耗时分析 | 1. 扩容 Worker<br>2. 取消低优先级任务<br>3. 调整预取数/并发数 | 积压 > 1h 未消减 → P1 |
| 定时任务未执行 | 1. Beat 进程检查<br>2. Schedule 状态<br>3. 时区/锁竞争 | 1. 重启 Beat<br>2. 手动触发补跑<br>3. 检查分布式锁 | 核心同步任务漏跑 → P1 |

### 5.4 外部依赖故障
| 故障现象 | 诊断步骤 | 标准处置 | 升级条件 |
|---------|---------|---------|---------|
| FXG/Creator API 限流/报错 | 1. 错误码分析 (429/5xx/签名失败)<br>2. 请求频率统计<br>3. Cookie/Token 有效性 | 1. 启用降级模式 (读缓存/返回静态数据)<br>2. 动态降低并发/请求频率<br>3. 刷新 Cookie/Token<br>4. 联系平台技术支持 | 核心数据源全挂 → P0 |
| DNS 解析失败 | 1. `dig` 验证<br>2. 切换 DNS 服务器<br>3. `/etc/hosts` 临时绑定 | 1. 使用 IP 直连 (临时)<br>2. 刷新本地 DNS 缓存<br>3. 联系云厂商/域名商 | 影响全站 → P0 |

### 5.5 安全事件
| 故障现象 | 诊断步骤 | 标准处置 | 升级条件 |
|---------|---------|---------|---------|
| 疑似数据泄露 | 1. 访问日志审计<br>2. 敏感字段加密核查<br>3. 数据血缘追踪 | 1. 立即隔离受影响系统<br>2. 启动取证流程<br>3. 法务/合规介入<br>4. 按法规上报 | 确认泄露 → P0 最高级响应 |
| 勒索软件/加密攻击 | 1. 文件系统异常监控<br>2. 进程/网络连接异常<br>3. 备份完整性校验 | 1. 物理隔离感染节点<br>2. 不支付赎金<br>3. 从离线备份恢复<br>4. 全网排查横向移动 | 确认感染 → P0 |

## 6. 通信与通知机制

### 6.1 内部通知
| 场景 | 渠道 | 模板 | 接收人 |
|------|------|------|--------|
| P0/P1 告警触发 | 企业微信群 + 电话 + PagerDuty | `[P0] 故障标题 - 影响范围 - 发现时间` | IC、TL、Ops、Comms |
| 状态更新 (每 30min) | 企业微信群 | `【更新】故障标题 - 当前进展 - 下一步动作 - 预计恢复时间` | 全响应组 |
| 故障恢复 | 企业微信群 + 邮件 | `【恢复】故障标题 - 恢复时间 - 根因摘要 - 验证结果` | 全响应组 + 业务方 |
| PIR 发布 | 企业微信群 + 文档链接 | `【PIR】故障标题 - 文档链接 - 改进项` | 全团队 |

### 6.2 外部通知 (业务方/用户)
| 场景 | 渠道 | 时机 | 内容要点 |
|------|------|------|---------|
| 核心功能不可用 | 企业微信/邮件/短信 | 确认影响范围后 15min 内 | 影响功能、预计恢复时间、临时绕行方案 |
| 计划维护窗口 | 邮件/公告 | 维护前 24h | 维护时间、影响范围、联系人 |
| 数据异常/不准确 | 企业微信/电话 | 确认后 1h 内 | 影响数据范围、修正计划、预计修正时间 |

## 7. 故障复盘 (PIR - Post-Incident Review)

### 7.1 PIR 触发条件
- 所有 P0、P1 故障
- 同一根因导致的 2 次以上 P2 故障
- 任何涉及数据丢失/安全的故障
- 业务方主动要求复盘的故障

### 7.2 PIR 文档结构
```markdown
# PIR-{编号}: {故障标题}

## 1. 基本信息
- 故障编号: INC-YYYYMMDD-XXX
- 严重等级: P0/P1/P2
- 发生时间: YYYY-MM-DD HH:MM - HH:MM
- 持续时长: XX 分钟
- 影响范围: 受影响店铺/用户/功能
- 事件指挥官: 姓名

## 2. 时间线
| 时间 | 事件 | 操作人 | 备注 |
|------|------|--------|------|
| 10:30 | 告警触发 | 监控系统 | - |
| 10:32 | IC 确认 P1 | 张三 | - |
| 10:35 | TL 定位根因 | 李四 | FXG API 返回 429 |
| 10:40 | 实施降级 | 王五 | 启用缓存读模式 |
| 10:45 | 业务验证通过 | 赵六 | - |

## 3. 根因分析 (5Why)
1. Why? 订单同步任务连续失败
2. Why? FXG API 返回 429 Too Many Requests
3. Why? 并发请求数超过平台限制 (20 QPS)
4. Why? 增量同步并发未做限流，突发流量触发限流
5. Why? 代码未实现令牌桶限流，配置未同步到所有 Worker

**根因**: 同步任务缺乏客户端限流机制，配置管理不一致

## 4. 影响评估
- 数据同步延迟: 2 小时
- 受影响店铺: 12 家
- 用户投诉: 3 单
- 收入影响: 无直接损失

## 5. 改进行动项
| 编号 | 改进措施 | 负责人 | 截止日期 | 状态 | 验收标准 |
|------|---------|--------|----------|------|----------|
| ACT-001 | 实现客户端令牌桶限流 (20 QPS) | 李四 | 2026-10-10 | 进行中 | 压测验证 100 并发不触发 429 |
| ACT-002 | 统一同步配置到 ConfigMap/Vault | 王五 | 2026-10-05 | 待开始 | 所有 Worker 读取统一配置 |
| ACT-003 | 增加限流指标监控告警 | 张三 | 2026-10-08 | 待开始 | Grafana 有限流仪表盘 |

## 6. 经验教训
- 配置分散导致行为不一致，需集中化管理
- 缺乏压测验证上游限流阈值
- 降级开关生效验证不足
```

### 7.3 PIR 会议
- **时间**: 故障恢复后 24-48 小时内
- **时长**: 30-60 分钟
- **参会**: IC、TL、Ops、Comms、相关 Owner
- **主持**: IC (非当事人)
- **产出**: PIR 文档、改进项录入缺陷系统

## 10. 附录

### 10.1 常用应急命令速查
```bash
# MySQL 主从切换
# 1. 从库提升为主
STOP SLAVE; RESET SLAVE ALL; SET GLOBAL read_only=OFF;
# 2. 其他从库指向新主
CHANGE MASTER TO MASTER_HOST='new_master_ip', MASTER_AUTO_POSITION=1; START SLAVE;

# Redis Sentinel 手动故障转移
redis-cli -h sentinel_ip -p 26379 SENTINEL FAILOVER mymaster

# Docker 服务重启 (优雅)
docker-compose -f docker-compose.prod.yml restart -t 30 backend

# 查看 Celery 任务堆积
docker-compose exec backend celery -A celery_app inspect active_queues

# 紧急熔断下游 API (Nginx 限流)
# 在 nginx.conf 中临时调整 limit_req_zone

# 证书紧急续期
certbot renew --force-renewal --nginx
systemctl reload nginx
```
