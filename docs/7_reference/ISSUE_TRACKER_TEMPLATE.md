## 1. 问题管理概述

### 1.1 目的
建立统一的问题追踪体系，确保：
- 所有问题可发现、可记录、可追踪、可度量
- 问题分类分级科学、处理流程标准化
- 关键指标 (MTTD/MTTR、缺陷漏测率、重开率) 可监控
- 知识沉淀形成组织资产

### 1.2 问题类型分类

| 问题类型 | 代码 | 定义 | 典型来源 | 处理 SLA |
|----------|------|------|----------|----------|
| **缺陷** | BUG | 系统行为与需求/设计/预期不符 | 测试发现、生产监控、用户反馈 | 按严重级别 |
| **任务** | TASK | 明确的工作项、交付物 | Sprint 规划、技术债、重构 | 迭代内完成 |
| **改进** | IMPROVEMENT | 非缺陷的优化建议 | 性能优化、体验提升、代码质量 | 纳入迭代规划 |
| **技术债** | TECH_DEBT | 为追求速度而妥协的技术决策 | 快速交付、临时方案、缺乏重构 | 专门 Sprint 偿还 |
| **安全漏洞** | SECURITY | CVE、配置不当、权限越界、数据泄露风险 | 扫描工具、渗透测试、审计 | P0: 24h, P1: 72h |
| **事件** | INCIDENT | 生产环境故障、服务中断、数据异常 | 监控告警、用户投诉、巡检 | 按事件等级 |
| **需求变更** | REQ_CHANGE | 新增/修改/删除需求 | 业务方提出、市场变化 | 走 CR 流程 |
| **疑问/咨询** | QUESTION | 技术方案澄清、需求细节确认 | 开发过程、代码评审 | 24h 内响应 |

## 3. 问题分诊与分级标准

### 3.1 严重级别定义

| 级别 | 代码 | 定义 | 典型示例 | 响应时间 | 解决目标 | 升级路径 |
|------|------|------|----------|----------|----------|----------|
| **Critical** | P0 | 系统完全不可用、核心数据丢失、安全重大漏洞、全站瘫痪 | 全站 5xx、数据库主库挂掉、RCE 漏洞、核心数据删除 | 15 分钟 | 1 小时 (止血) / 4 小时 (根治) | 立即升级至 Tech Lead + PM + Sponsor |
| **High** | P1 | 核心功能不可用、SLA 严重违约、数据不一致、安全高危漏洞 | 核心 API 5xx > 5%、同步任务全量失败、认证绕过、PII 泄露 | 30 分钟 | 4 小时 (止血) / 24 小时 (根治) | 1 小时升级至 Tech Lead + PM |
| **Medium** | P2 | 非核心功能异常、性能退化、非核心数据问题、安全中危漏洞 | 非核心 API 报错、Dashboard 个别组件报错、同步延迟 > 30 分钟 | 4 小时 | 24 小时 (止血) / 3 天 (根治) | 8 小时升级至 Tech Lead |
| **Low** | P3 | 体验问题、UI 瑕疵、非核心报错、文档错误、安全低危漏洞 | UI 对齐偏差、拼写错误、非关键日志报错、信息泄露 (非敏感) | 1 天 | 下个 Sprint | 无自动升级 |
| **Cosmetic** | P4 | 纯文案/样式/非功能性优化 | 文案优化、颜色微调、代码格式化 | 无硬性要求 | 纳入 Backlog | 无 |

### 3.2 优先级矩阵 (优先级 ≠ 严重级别)

| 严重级别 \ 业务紧迫度 | 紧急 (本周必须) | 高 (本迭代) | 中 (下迭代) | 低 (Backlog) |
|----------------------|-----------------|-------------|-------------|--------------|
| **P0 Critical** | **P0** | **P0** | **P0** | **P0** |
| **P1 High** | **P0** | **P1** | **P1** | **P2** |
| **P2 Medium** | **P1** | **P2** | **P2** | **P3** |
| **P3 Low** | **P2** | **P3** | **P3** | **P4** |
| **P4 Cosmetic** | **P3** | **P4** | **P4** | **P4** |

> **规则**: 严重级别由技术事实决定，优先级由业务紧迫度+严重级别联合决定。P0 级别问题必须立即响应，不受优先级矩阵限制。

## 4. 问题生命周期流程

```mermaid
stateDiagram-v2
    [*] --> New: 新建 Issue
    New --> Triage: PM/QA 分诊 (≤ 4h)
    Triage --> Assigned: 确认优先级、指派人
    Triage --> Duplicate: 标记重复 -> Closed
    Triage --> Won't Fix: 评估不予修复 -> Closed
    Triage --> Need Info: 信息不足 -> 等待补充 -> Triage
    
    Assigned --> In Progress: 开发开始
    In Progress --> Code Review: PR 提交
    Code Review --> Changes Requested: 驳回 -> In Progress
    Code Review --> Approved: 通过
    Approved --> Ready for Test: 部署测试环境
    Ready for Test --> In Testing: QA 开始验证
    In Testing --> Verified: 验证通过
    In Testing --> Rejected: 驳回 -> In Progress
    Verified --> Ready for Release: 等待发布窗口
    Ready for Release --> Deployed: 生产发布
    Deployed --> Monitoring: 观察期 (1-24h)
    Monitoring --> Verified in Prod: 生产验证通过
    Verified in Prod --> Closed: 关闭
    
    Monitoring --> Hotfix: 发现回归 -> Hotfix 分支
    Hotfix --> Code Review
    
    Closed --> Reopened: 复现/遗漏 -> Triage
    
    note right of Triage: SLA: P0/P1 ≤ 4h\nP2 ≤ 1天\nP3 ≤ 3天
    note right of In Progress: SLA: P0 ≤ 4h\nP1 ≤ 24h\nP2 ≤ 3天
    note right of Monitoring: 观察期: P0/P1=1h\nP2=4h\nP3=24h
```

## 5. 关键指标与度量

### 5.1 核心指标 (KPIs)

| 指标 | 定义 | 目标 | 统计口径 | 统计频率 | 负责人 |
|------|------|------|----------|----------|--------|
| **MTTD** (Mean Time To Detect) | 从故障发生到被检测的平均时间 | < 5 分钟 (P1) | 所有 P1/P2 事件 | 周度 | DevOps |
| **MTTR** (Mean Time To Resolve) | 从检测到问题完全解决的平均时间 | P0: < 1h<br>P1: < 4h<br>P2: < 24h | 已关闭的 P0/P1/P2 | 周度 | DevOps + PM |
| **缺陷漏测率** | 生产发现 / (生产发现 + 测试发现) | < 5% | 发布后 30 天内 | 发布后 | QA |
| **缺陷重开率** | 关闭后被 Reopen / 总关闭数 | < 3% | 最近 30 天关闭 | 周度 | QA |
| **缺陷修复周期** | 从 Assigned 到 Verified 平均时长 | P0: < 4h<br>P1: < 24h<br>P2: < 72h | 已关闭按严重级分组 | 周度 | PM |
| **技术债偿还率** | 本迭代关闭技术债 / 积累技术债 | ≥ 1.0 | 迭代级 | 迭代级 | Tech Lead |
