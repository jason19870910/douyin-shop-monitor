# Code Review 指南

## 1. 目的与原则

### 1.1 核心目的
- **质量把关**：在合并前发现缺陷、安全隐患、性能问题
- **知识传递**：让团队了解代码变更、分享最佳实践、降低 Bus Factor
- **规范执行**：确保编码规范、架构原则、安全要求落地
- **团队协作**：建设性反馈、相互学习、共同进步

### 1.2 审查原则
| 原则 | 说明 |
|------|------|
| **尊重与建设性** | 评论代码不评论人，提供具体改进建议而非批评 |
| **关注实质** | 优先关注正确性、安全性、可维护性，风格问题交给工具 |
| **及时响应** | 24 小时内首次 Review，阻塞性问题 2 小时内响应 |
| **小步快跑** | 单次 PR < 400 行，拆分大 PR，便于深度 Review |
| **自动化优先** | Lint/Format/Type Check/测试全自动化，人工聚焦逻辑与设计 |

---

## 2. 审查流程

### 2.1 角色与职责
| 角色 | 职责 | SLA |
|------|------|-----|
| **Author (提交者)** | 自检、编写清晰 PR 描述、回应评论、修复问题 | - |
| **Reviewer (审查者)** | 深度阅读代码、提出建设性反馈、Approve/Request Changes | 首次 Review ≤ 24h |
| **Tech Lead (技术负责人)** | 核心模块/架构变更最终把关、裁决争议 | 关键 PR ≤ 4h |
| **QA (测试工程师)** | 验证测试覆盖、复现缺陷、回归风险评估 | 测试相关 PR ≤ 8h |

### 2.2 审查触发条件
| 触发条件 | 说明 |
|----------|------|
| PR 创建/更新 | 自动触发 CI、通知 Reviewer |
| Author 标记 "Ready for Review" | 正式进入审查队列 |
| Reviewer 请求变更 | Author 修复后重新请求 Review |
| 关键路径变更 | 自动添加 Tech Lead/架构师为必选 Reviewer |

## 3. 审查清单 (核心维度)

### 3.1 正确性与完整性
- [ ] **需求对齐**：代码是否完整实现了 Issue/PR 描述的需求？
- [ ] **边界处理**：空值、空数组、超长输入、并发边界、时区/编码
- [ ] **错误处理**：异常捕获、错误码规范、用户友好提示、日志记录
- [ ] **事务一致性**：数据库操作原子性、分布式事务补偿、幂等性
- [ ] **并发安全**：竞态条件、死锁预防、乐观/悲观锁正确使用

### 3.2 安全性
- [ ] **输入验证**：所有外部输入（参数、Header、Body、文件）严格校验白名单
- [ ] **SQL 注入防护**：ORM 参数化查询，禁止字符串拼接 SQL
- [ ] **XSS/CSRF 防护**：输出编码、CSP、SameSite Cookie、CSRF Token
- [ ] **认证授权**：资源级权限校验、所有权检查、最小权限原则
- [ ] **敏感数据**：无硬编码密钥、日志脱敏、加密传输/存储、密钥轮换
- [ ] **依赖安全**：无已知高危漏洞 (CVE)、依赖版本锁定、SBOM 生成

### 3.3 性能与可扩展性
- [ ] **数据库**：无 N+1 查询、索引覆盖、分页游标、大事务拆分
- [ ] **缓存**：Key 设计合理、TTL 设置、穿透/击穿/雪崩防护、一致性策略
- [ ] **并发控制**：连接池大小、超时设置、熔断降级、背压处理
- [ ] **资源释放**：连接/文件/句柄及时关闭、大对象流式处理
- [ ] **算法复杂度**：避免 O(n²) 循环、大数据量分批处理

### 3.4 代码质量与可维护性
- [ ] **单一职责**：函数/类职责单一、长度适中 (函数 < 50 行、类 < 300 行)
- [ ] **命名规范**：语义清晰、无缩写歧义、领域术语统一
- [ ] **复用与抽象**：DRY 原则、公共逻辑提取、避免过度设计
- [ ] **类型安全**：TypeScript/Python 严格模式通过、无 `any` 滥用
- [ ] **文档注释**：公共 API 必须有 Docstring/TSDoc、复杂逻辑有行内注释

### 3.5 测试覆盖
- [ ] **单元测试**：核心逻辑覆盖 ≥ 80%、边界/异常路径覆盖、Mock 外部依赖
- [ ] **集成测试**：关键链路验证 (API/DB/外部服务/消息队列)
- [ ] **契约测试**：Provider/Consumer 契约一致性
- [ ] **测试质量**：测试代码可读、无 Flaky Test、测试数据隔离

### 3.6 架构与设计
- [ ] **分层清晰**：Controller/Service/Repository/Entity 分层合理
- [ ] **依赖方向**：核心域不依赖基础设施、依赖倒置
- [ ] **模块边界**：高内聚低耦合、循环依赖检测通过
- [ ] **配置外部化**：无硬编码、环境变量/配置中心管理
- [ ] **向后兼容**：API 不破坏现有客户端、Breaking Change 有迁移方案

## 4. 审查技巧与工具

### 4.1 高效阅读代码
| 技巧 | 说明 |
|------|------|
| **先看测试** | 理解预期行为、边界场景、业务规则 |
| **看接口再看实现** | 先理解 API 契约、数据流向、再看细节 |
| **关注变更上下文** | GitHub/GitLab "Files changed" 视图，关注修改前后对比 |
| **运行本地验证** | 复杂逻辑拉取分支本地跑测试、调试 |

### 4.2 评论最佳实践
| 评论类型 | 格式示例 | 适用场景 |
|----------|----------|----------|
| **建议修改** | `建议: 这里用 `user_id` 而非 `uid`，保持命名一致性` | 命名、风格、最佳实践 |
| **提问澄清** | `疑问: 这里为什么用 `list` 而非 `set`？是否有序要求？` | 逻辑不清、设计决策不明 |
| **指出风险** | `⚠️ 风险: 并发场景下可能丢失更新，建议加乐观锁` | 并发、安全、性能隐患 |
| **要求修复** | `🔴 必须修复: 直接拼接 SQL 存在注入风险，请用参数化查询` | 安全、正确性阻塞项 |
| **赞扬/学习** | `👍 这里用 `functools.lru_cache` 很巧妙，学习了` | 优秀实践、知识分享 |

### 4.3 评论礼仪
| 原则 | 正例 | 反例 |
|------|------|------|
| **具体可操作** | `建议将此处提取为 `calculate_tax` 函数，便于复用和测试` | `这段代码写得不好` |
| **区分阻塞/建议** | `🔴 必须修复: ...` / `💡 建议: ...` | 混淆优先级 |
| **提供替代方案** | `建议改用 `dict.get(key, default)` 避免 KeyError` | 只指出问题不给方案 |
| **避免人身攻击** | `这段逻辑容易引起并发问题` | `你写的代码有问题` |
| **及时跟进** | Author 修复后及时 Re-review，勾选 Resolved | 留存未解决评论 |

## 5. 审查规模与拆分策略

### 5.1 PR 规模控制
| 规模 | 建议行数 | 审查时长 | 策略 |
|------|----------|----------|------|
| **小** | < 100 行 | 10-15 分钟 | 直接审查 |
| **中** | 100-400 行 | 20-30 分钟 | 分模块审查 |
| **大** | 400-800 行 | 40-60 分钟 | **拆分为多个 PR** |
| **超大** | > 800 行 | > 1 小时 | **强制拆分**，按功能/层级拆分 |

### 5.2 大 PR 拆分策略
| 拆分维度 | 示例 |
|----------|------|
| **按层级** | 1) 数据库迁移 2) Repository 层 3) Service 层 4) API 层 5) 前端组件 |
| **按功能** | 1) 核心 CRUD 2) 导出功能 3) 筛选/搜索 4) 权限控制 |
| **按依赖** | 1) 基础设施/配置 2) 核心领域模型 3) 业务逻辑 4) 接口暴露 |
| **按风险** | 1) 低风险重构/工具函数 2) 核心业务逻辑 3) 外部集成/安全相关 |

## 6. 审查决策与后续

### 6.1 审查结论
| 结论 | 含义 | 后续动作 |
|------|------|----------|
| **Approve** | 代码质量达标，可以合并 | Author 可合并 (或自动合并) |
| **Request Changes** | 存在必须修复的问题 | Author 修复后重新请求 Review |
| **Comment** | 仅有建议性意见，无阻塞项 | Author 可自行决定是否采纳 |

### 6.2 常见拒绝理由
| 类别 | 典型理由 |
|------|----------|
| **正确性** | 逻辑漏洞、边界未处理、并发不安全、数据不一致 |
| **安全性** | 注入风险、权限绕过、敏感信息泄露、依赖漏洞 |
| **性能** | N+1 查询、无索引全表扫描、内存泄漏、阻塞调用 |
| **可维护性** | 硬编码、重复代码、过度耦合、命名混乱、无测试 |
| **规范性** | 破坏性变更无迁移、API 不规范、配置硬编码、文档缺失 |

## 7. 审查文化建设

### 7.1 团队公约
| 公约内容 | 执行方式 |
|----------|----------|
| **人人参与 Review** | 轮值 Reviewer 机制、Review 贡献计入绩效 |
| **新人导师制** | 新入职前 3 个月指定 Mentor 陪同 Review |
| **Review 复盘** | 月度 Review 复盘会，总结高频问题、优化清单 |
| **知识分享** | 优秀 Review 案例归档、月度分享会 |
| **零容忍恶意评论** | 发现人身攻击、非建设性批评零容忍 |

### 7.2 Review 质量度量
| 指标 | 目标 | 统计方式 |
|------|------|----------|
| 平均首次 Review 时间 | < 4 小时 (P0) / < 24 小时 (常规) | GitHub/GitLab API 统计 |
| 平均 Review 轮数 | ≤ 2 轮 | PR 活动记录 |
| 缺陷发现率 (Review 阶段) | > 60% 缺陷在 Review 发现 | 缺陷来源分析 |
| 审查覆盖率 | 100% PR 有 Review | 分支保护强制 |
| Reviewer 参与度 | 人均月 Review ≥ 8 个 | 贡献统计 |

## 8. 常见审查场景速查

| 场景 | 重点关注 | 典型问题 |
|------|----------|----------|
| **新增 API** | RESTful 设计、参数校验、错误码、文档、测试 | 缺少分页、错误码不规范、无鉴权 |
| **数据库迁移** | 向后兼容、回滚脚本、大表在线变更、索引策略 | 无回滚、锁表风险、字段默认值缺失 |
| **外部集成** | 超时/重试/熔断、签名验证、幂等性、降级预案 | 无超时、无重试、敏感信息日志 |
| **重构/重命名** | 影响范围评估、全链路搜索替换、废弃标记、迁移指南 | 漏改调用处、破坏兼容性、文档未同步 |
| **性能优化** | 基线对比、压测报告、监控埋点、回滚方案 | 无基线对比、伪优化、引入新 Bug |
| **安全修复** | 根因分析、影响范围、补丁验证、CVE 编号 | 仅治标不治本、未验证修复、未轮换密钥 |

## 9. 审查工具与自动化

### 9.1 必备工具链
| 工具 | 用途 | 集成方式 |
|------|------|----------|
| **GitHub/GitLab PR** | 核心审查平台 | 原生 |
| **Code Review Checklist** | 结构化审查 | PR 模板/插件 |
| **SonarQube/CodeQL** | 静态分析、安全扫描 | CI 集成、PR 装饰 |
| **Dependabot/Renovate** | 依赖更新 PR 自动创建 | 定时任务 |
| **Pre-commit Hooks** | 本地预检查 | `pre-commit install` |
| **GitHub Actions/GitLab CI** | 自动化门禁 | `required_status_checks` |

### 9.2 审查辅助配置
```yaml
# .github/PULL_REQUEST_TEMPLATE.md (关键片段)
## 变更类型
- [ ] feat / [ ] fix / [ ] refactor / [ ] perf / [ ] docs / [ ] test / [ ] chore

## 核心检查 (Author 自检)
- [ ] 通过 `lint`/`type-check`/`test`/`build`
- [ ] 单元测试覆盖新增逻辑 (≥80% 核心模块)
- [ ] 更新文档 (README/CHANGELOG/API/注释)
- [ ] 无破坏性变更，或已提供迁移指南

## 审查重点 (Reviewer 关注)
- [ ] 正确性/边界/异常处理
- [ ] 安全性 (注入/权限/敏感数据)
- [ ] 性能 (N+1/索引/缓存/并发)
- [ ] 可维护性 (命名/复用/类型/测试)
- [ ] 架构合规 (分层/依赖/兼容性)
```

## 10. 审查反模式与避坑

| 反模式 | 表现 | 危害 | 纠正措施 |
|--------|------|------|----------|
| **橡皮图章** | 快速 Approve，未细读代码 | 漏缺陷、形式主义 | 强制 Checklist、最小审查时长、Review 质量考核 |
| **事无巨细** | 纠结缩进、换行、变量名偏好 | 浪费时间、打击积极性 | 交给 Formatter/Linter、约定风格指南 |
| **推迟 Review** | PR 挂起数天 | 阻塞交付、上下文丢失 | SLA 考核、自动提醒、轮值 Reviewer |
| **只看不评** | 只看不发表评论 | 知识不传递、问题不暴露 | 最少 1 条评论/建议、鼓励提问 |
| **争论不休** | 风格偏好争论、不设截止 | 消耗精力、延误合并 | 约定风格指南、Tech Lead 裁决、约定优于配置 |

## 10. 附录：Review 模板

```markdown
# Code Review Checklist (Reviewer 使用)

## 基础检查 (必看)
- [ ] PR 描述清晰：What/Why/How、关联 Issue
- [ ] CI 全绿：Lint、Type Check、Test、Build、Security Scan
- [ ] 无明显冲突、基于最新 develop/main
- [ ] Commit Message 规范、无 fixup!/wip! 提交

## 核心维度 (逐项勾选)
### 正确性
- [ ] 业务逻辑符合预期
- [ ] 边界条件处理 (空/异常/并发/极值)
- [ ] 错误处理完善、错误码规范

### 安全性
- [ ] 输入验证/输出编码
- [ ] 认证授权/资源级权限
- [ ] 无硬编码密钥/敏感信息
- [ ] SQL/命令注入防护

### 性能
- [ ] 无 N+1/全表扫描
- [ ] 缓存策略合理
- [ ] 并发/资源控制

### 代码质量
- [ ] 命名规范/单一职责
- [ ] 类型注解完整
- [ ] 复用/抽象合理
- [ ] 文档注释完善

### 测试
- [ ] 单测覆盖核心逻辑
- [ ] 集成测试关键链路
- [ ] 无 Flaky Test

## 评论汇总
### 🔴 必须修复 (阻塞合并)
1. 

### 🟡 建议改进 (可选采纳)
1. 

### 🟢 优秀实践 (值得学习)
1. 

## 结论
- [ ] Approve
- [ ] Request Changes
- [ ] Comment Only

Reviewer: @xxx
Date: YYYY-MM-DD
```
